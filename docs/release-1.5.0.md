## 3. 必须修改旧定时器

进入同一个 `bridge-api` 的定时触发器配置，找到 **bridge-retention-cleanup**，把每5分钟改成每天一次。必须替换旧周期，不能保留旧任务再加一个每日任务。

目标：北京时间每日03:00。按控制台显示的触发器时区选择：

| 控制台触发器时区 | 7段Cron |
| --- | --- |
| UTC+8 / Asia/Shanghai / 北京时间 | `0 0 3 * * * *` |
| UTC / UTC+0 | `0 0 19 * * * *` |

交付JSON使用第一行。若控制台使用UTC，请先把JSON中的config改为第二行，或直接在表单填写。运行环境的时区不等于触发器时区。保存后检查下一次执行时间是否为北京时间03:00。

只把JSON传进函数代码目录不会启用定时器。官方参考：[定时触发器](https://docs.cloudbase.net/cloud-function/timer-trigger)、[时区核对](https://docs.cloudbase.net/recipes/schedule-cloud-function-cron-job)。

每次执行对临时记录、孤立附件分块、到期来信、孤立投票记录四组各最多删除100条，不循环清空。临时记录组含会话、验证码、票据、限流与到期上传清单，共用100条上限。有积压时会分多天处理。日志 `bridge_cleanup_complete` 包含各组实际删除数；`bridge_cleanup_failed` 表示失败。持续多天某组都达到100，应查看积压并再评估清理方案，不能据此认定已经清完。

首次回复满30天仍立即不能查询、追加或回复；每日物理删除有延迟。未回复信件不受30天规则影响。查询恰好访问过期信件时仍可能顺便删除该封，不会触发全库清理。

## 4. 工作人员与管理员怎么使用

普通工作人员在通知/投票页面填写内容，选择「保存草稿」或「提交审核」。普通工作人员的新增、修改、已发布内容删除、提前结束投票，以及票数/占比展示设置修改都需审核。学生在审核通过前看不到新稿，旧稿继续展示。

全体工作人员共享「投稿记录」：可查看全部投稿、草稿、待审核、已通过、已驳回和已撤回记录。待审核稿必须先撤回再编辑；已驳回稿可按原因修改后重新提交。未发布草稿可以直接删除。

**最高管理员是现有 bridge.admin。** 后端按owner权限授权，不靠客户端隐藏按钮判断。登录后增加「审核中心」「系统更新」。审核中心可对照当前线上版和提交版，预览附件，选择通过或填写原因驳回。管理员自己从通知/投票页面发布可直接上线；编辑共享稿件走投稿流程。

管理员直接修改、删除或结束有待审核申请的内容时，会再次询问是否使申请失效。取消则不改变任何内容。

投票审核时必须尚未到截止时间。修改审核期间如果已有投票，题目、选项等修改会被拒绝，需驳回重新处理；已有票数不会覆盖。定时通知审核通过后，未来发布时间仍等待，到期已过则立即可见。

公开页面更新记录只写学生相关变化；后台完整历史只由管理员的受保护接口读取。「系统更新」不对普通工作人员开放。来信回复与删除权限不变。

## 5. 上线验收与消耗观察

1. 用普通工作人员创建一条测试通知，确认显示已提交审核且学生端看不到。
2. 用bridge.admin在审核中心通过，确认学生端可见；再测试修改送审时旧版仍在。
3. 测试一条投票，核对审核、截止时间、选项及提交；测试内容用管理员删除。
4. 确认触发器是每日一次，并检查下一次实际调用日志，不要只看健康接口。
5. 记录上线前的PostgreSQL CU和资源点，24–48小时后比较按小时用量，并结合真实访问量。关闭无需使用的SQL控制台/测试页面，避免其他来源访问影响对比。

本次实测的是请求/SQL次数下降，不承诺固定资源点节省比例。共享PostgreSQL按有活动的5分钟时段计量；即使SQL变少，处于同一活跃时段的费用未必同比例减少。[官方计量说明](https://docs.cloudbase.net/database/postgresql/database-management)
